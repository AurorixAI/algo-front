# E2E-тесты ALGO (Playwright)

Герметичный прогон реального UI в браузере: тесты **сами поднимают свой стек** (Postgres + Redis + auth-service
в Docker, фронт — `next build && next start` из этого чекаута), создают данные через API и проверяют экраны так,
как их видит пользователь. Ни stage, ни prod, ни чужие контейнеры не затрагиваются (ROADMAP #27).

## Запуск

```bash
npm install                      # один раз (Playwright — devDependency)
npx playwright install chromium  # один раз (браузер)
npm run e2e                      # стек вверх → сборка фронта → тесты → стек вниз
```

Нужны: Docker Desktop, Node 20, чекаут auth-service (по умолчанию `../auth-service-n13p2` — ветка, которая на stage).
Сценарий онлайн-экзамена (`@exam`) идёт только с `E2E_EXAM=1` и требует ещё чекаут exam-service (`../exam-service-n13`);
первая сборка его образа долгая (apt ставит Chromium для PDF, ~15-20 мин), дальше слои берутся из кэша Docker.

| Команда | Что делает |
|---|---|
| `npm run e2e` | весь набор (desktop 1280×800 + mobile 375×812 для тестов с `@mobile`), потом полный teardown |
| `npm run e2e -- --project=mobile` | только телефон; любые флаги Playwright: `-g "архив"`, `owner-payroll`, `--repeat-each=3` |
| `npm run e2e:ui` | то же, но браузер виден (`--headed`) |
| `E2E_EXAM=1 npm run e2e` | то же + exam-service, заглушка content-service и сценарий онлайн-экзамена |
| `E2E_KEEP=1 npm run e2e` | оставить стек и фронт после прогона (разработка тестов) |
| `E2E_REUSE=1 npm run e2e -- <spec>` | не пересобирать: использовать уже поднятый стек и готовый `.next-e2e` (прогон ~3 с) |
| `npm run e2e:down` | остановить то, что оставил `E2E_KEEP` (только свои процессы и контейнеры проекта `algo-e2e`) |
| `npm run e2e:report` | HTML-отчёт последнего прогона; трейсы падений — в `e2e/test-results/` |
| `npm run e2e:typecheck` | `tsc` по `e2e/` |

Переменные окружения: `AUTH_SERVICE_PATH` (чекаут auth-service), `EXAM_SERVICE_PATH`, `E2E_EXAM`, `E2E_FRONT_PORT` (13000), `E2E_AUTH_PORT` (18000), `E2E_EXAM_PORT` (18003),
`E2E_WORKERS` (параллельные воркеры, по умолчанию 3), `E2E_SKIP_BUILD=1` (не пересобирать фронт, если есть `.next-e2e`).
Порты выбраны так, чтобы не пересекаться с обычной разработкой (3000/8000); если порт занят чужой программой,
раннер остановится с понятной ошибкой и **ничего не убьёт**.

## Как устроен стек

* `e2e/docker-compose.e2e.yml`, проект `algo-e2e`: `db` (Postgres 15, данные в tmpfs — база рождается пустой на каждый
  прогон), `redis`, `auth` (образ из `AUTH_SERVICE_PATH`, Alembic применяется при старте). `APP_ENV=development`:
  подключён `/auth/dev-login`, а cookie авторизации идут **без `Secure`** (Secure только для staging/production,
  `cookies_are_secure()`), поэтому http://localhost работает.
* Профиль `exam` (`E2E_EXAM=1`): `exam` (образ из `EXAM_SERVICE_PATH`, своя база `exam-db`, тот же внутренний токен и Redis),
  `content-stub` — ~150 строк стандартной библиотеки Python (`e2e/stubs/content_stub.py`), которые отвечают на read-API
  content-service, нужный exam-service (задания, учебник, оглавление, навыки). Настоящему content-service нужен оцифрованный банк
  заданий; для сценария хватает пяти честных заданий с известными ответами («Найдите сумму чисел три и четыре» → 7, числа
  словами, потому что фронт рисует голые числа через KaTeX, невидимый для дерева доступности). Заглушка повторяет форму
  ответа `_task_row_full` настоящего сервиса; если она разойдётся с ним, exam-service это заметит (тест упадёт на создании черновика).
* Фронт собирается в отдельную папку `.next-e2e` (`NEXT_DIST_DIR`, обычный `.next` и `next dev` не трогаются) с
  `NEXT_PUBLIC_AUTH_API_URL=http://localhost:18000` и запускается `next start -p 13000`. У фронта нет same-origin
  прокси/rewrites, API вызывается кросс-доменно с `credentials: include`; cookie — host-only для `localhost`, общие для
  портов 13000 и 18000, поэтому браузер всегда открывает **`localhost`** (не `127.0.0.1`).
* Teardown: `docker compose down -v` и остановка процесса фронта, который запустил этот же раннер (pid в `e2e/.state`).

## Данные и вход

Каждый spec-файл создаёт **свою организацию** (`Org.create` в `support/api.ts`: `/auth/apply` → `/auth/login`, затем
приглашения и `accept` для учителей/админов, группы, ученики, оплаты — всё через API). Поэтому файлы независимы и идут
параллельно, а настройки организации («Единый день оплаты», право админа) и ведомости зарплаты одной проверки не влияют
на другую. Логины/пароли — случайные, живут только в памяти процесса, в логи не попадают; стек одноразовый.
`/auth/dev-login` (без пароля) проверяет `auth-dev-login.spec.ts`: роли owner/teacher/admin, cookie httpOnly и не Secure.

* **Уроки «сегодня»**: API не создаёт урок, начало которого раньше «сейчас», и не даёт начать урок раньше времени, поэтому
  `createLessonStartingNow` ставит повторяющийся урок на сегодняшний день недели с началом в текущую минуту
  *по часам сервера* (Asia/Tashkent), концом +10 мин (кнопка «Завершить урок» открывается за 15 мин до конца — то есть сразу)
  и ждёт, пока часы сервера и машины дойдут до этой минуты. Урок остаётся доступным до полуночи. Запуск в последние ~15 минут
  суток по Ташкенту (UTC+5, т.е. 18:45–19:00 UTC) даёт понятную ошибку: перезапустите чуть позже.
* **Ожидаемые числа считает тест сам** (`support/time.ts`: «месяц минус день», биллинговый период, пропорция по урокам с
  округлением до 1000, зарплатная формула целочисленно), а не берёт из ответа API.
* **Лимит входа** auth-service считается по адресу из `X-Real-IP` (в проде его выставляет nginx). Без nginx раннер играет его
  роль: каждый API-клиент теста шлёт свой адрес — иначе два прогона подряд упираются в 30 входов/мин. Сам лимитер не тронут.

## Сценарии

| Файл | Что проверяет | Проекты |
|---|---|---|
| `auth-dev-login.spec.ts` | dev-login трёх ролей, cookie не Secure, редирект на /login без сессии | desktop |
| `teacher-lesson.spec.ts` | дашборд → «Начать урок» → «Был»/«Ув.» (причина ≥3 символов) → «Сохранить отметки» → «Завершить урок» → «Завершён»; журнал в API | desktop, mobile |
| `owner-excuses.spec.ts` | «Посещаемость» → ожидающий пропуск со сроком (оплачен: `valid_to − 5 дн.`, не оплачен: конец месяца) → «Подтвердить» → ушёл из «Ожидают», виден в «Подтверждено» | desktop |
| `owner-payments.spec.ts` | быстрая оплата новичка (сумма вводится в строке) → «Оплачено» → история «№ N» → квитанция с суммой прописью → отмена с причиной (штамп «АННУЛИРОВАНА») | desktop (+ @mobile вёрстка) |
| `owner-fixed-day.spec.ts` | настройки «Оплаты» → «Единый день оплаты» → ученик, пришедший сегодня: «Неполный месяц», сумма = `round1000(fee × уроков в части / уроков в периоде)` по расписанию, «+ следующий месяц», чек | desktop |
| `owner-payroll.spec.ts` | проценты (62,5 и 40) → «Рассчитать всех» → итоги по формуле (с ожидающей «Ув.?» и неоплаченным уроком) → сохранить → правка оплаты → «редакция 2» → «История редакций» | desktop |
| `owner-archive.spec.ts` | «⋯» → «В архив» → нет в составе группы и в «Оплачено» → вкладка «Архив» → «Вернуть из архива» → снова в группе, история оплат цела; возврат в группу, ставшую полной: диалог остаётся с пояснением, карточка за ним уже «восстановлена», «Готово» только закрывает | desktop |
| `owner-payments-filter.spec.ts` | фильтр «преподаватель → группа»: открыть, раскрыть учителя, выбрать группу, выбрать учителя, сброс; на 375px панель целиком в окне | desktop, mobile |
| `exam-live.spec.ts` (`@exam`) | черновик → «Назначить занятие» (начатый урок) → «Назначить и открыть лобби» → код; ученик в **другом контексте браузера**: чужой ID не пускает, свой → «Вы в комнате ожидания»; учитель «Начать экзамен»; ученик отвечает двухшаговым выбором (1-е нажатие `aria-pressed="mixed"`, 2-е подтверждает и листает; на телефоне — настоящие touch-тапы), вопрос 2 нарочно неверно → «Завершить»; учитель: «Сдал», 2/3, 67 % | desktop, mobile |
| `permissions.spec.ts` | админ без права «Оплаты» не видит меню/вкладку/страницу (и сервер отвечает 403), с правом видит (но не «Зарплату»); учитель: `/owner/*` → его дашборд, в карточке ученика нет «Оплаты» | desktop |

Селекторы — доступные (`getByRole` / `getByLabel` / `getByText` с русскими подписями), поэтому тесты заодно проверяют
доступность; `data-testid` не добавлялись.

## Что не покрыто

* Банк заданий настоящего content-service, генерация вариантов/печатных комплектов и PDF (в экзамене — только онлайн-режим, одна
  версия, пять заданий из заглушки); создание экзамена через мастер `/teacher/exams/new` (черновик создаётся API, проверяется
  назначение на занятие и дальше).
* Диагностика (diagnostic-service; в карточке ученика «Диагностика и отчёты» показывает ошибку подключения — тесты это не проверяют),
  лендинг, Excel-экспорт зарплаты, печать.
* Уроки в прошлом и «пропущенные уроки»: API не позволяет создать их задним числом, а время в стеке не подменяется.
* Поведение вокруг полуночи по Ташкенту и смена месяца.

## Находки продукта (найдены при разработке набора, исправлены)

Все три находки закрыты в пакете «хвосты N13» (ROADMAP, реестр: №95, №96, №97, №98):

* **Гонка префикса ID учеников (№96).** Два центра с одинаковыми инициалами, впервые зачисляющие ученика одновременно,
  получали 500. Теперь префикс назначается в SAVEPOINT с повтором следующего кандидата (auth-service).
* **Зависание exam-service под нагрузкой класса (№95, №98).** Асинхронные обработчики держали синхронную сессию БД и ждали
  auth при открытой транзакции. Теперь ожидание вне транзакции, блокируется только попытка ученика, заданы `lock_timeout` /
  `statement_timeout` / `idle_in_transaction_session_timeout`; класс 60 учеников проходит 60/60.
* **Подписи полей не были связаны с полями (№97).** Теперь `Input` связывает `<label>` с полем; тесты ищут поля по подписи
  (`getByLabel`), а не по placeholder.

## CI

`.github/workflows/e2e.yml` — только ручной запуск (`workflow_dispatch`, входы `auth_ref`, `with_exam`). Репозиторий auth-service
(`AurorixAI/auth-services`) приватный, поэтому job читает его по секрету **`E2E_REPO_TOKEN`** (токен с правом чтения
содержимого этого репозитория). Секрет должен создать владелец репозитория; без него job сразу падает с понятным сообщением.
Когда секрет появится, добавьте в `on:` блок `pull_request: { branches: [develop] }` — набор пойдёт на каждый PR.
Отчёт и трейсы выкладываются артефактами.

## Как добавить сценарий

1. Новый `tests/<name>.spec.ts`; `test.beforeAll` → `org = await Org.create("Метка")`.
2. Данные — методами `Org` (`addStaff`, `createGroup`, `addStudent`, `pay`, `createLessonStartingNow`, `runLesson` ...);
   каждому тесту — свои ученики/группы с уникальными именами.
3. Вход — `const page = await signIn(org.owner | staff)` (отдельный контекст браузера на каждого человека).
4. Тест для телефона — добавьте `@mobile` в название: он пойдёт и в проекте `mobile`.
